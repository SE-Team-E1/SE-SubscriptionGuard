== 1. Sprintziel und zentrale Fragestellung
[cols="1,3", options="header"]
|===
| Kriterium | Ihre Antwort

| Sprintziel
a|
Ziel des zweiten Sprints war es, den technischen Ansatz für SubscriptionGuard zu testen, die Machbarkeit nachzuweisen, dass das Produkt mit dem gewählten Tech-Stack (Django + REST API + Docker + nginx) umsetzbar ist. Konkret sollte ein lauffähiges Walking Skeleton entstehen und wichtige Architekturentscheidungen durch Spikes und Domänenarbeit begründet werden.

| Zentrale technische Unsicherheit / Annahme
a|
Die zentrale Unsicherheit war, ob ein Django-Backend mit REST-API-Architektur die Kernfunktionen des Abo-Managements reproduzierbar und containerisiert abdecken kann. Eine weitere offene Frage war, wie mit dem Anforderungskonflikt zwischen Offline-Nutzung (Gastmodus), Multi-Device-Synchronisation und DSGVO-Konformität umzugehen ist — konkret: welche Synchronisationsstrategie das Produkt tragfähig macht.
|===

== 3. Wichtigste technische Lernergebnisse aus Sprint 2
[cols="1,3", options="header"]
|===
| Kriterium | Ihre Antwort

| Walking Skeleton bestätigt technische Machbarkeit
| Django + REST API können Kern-Abo-Daten verarbeiten. Die Tags v0.0.1–v0.0.5 belegen einen voll funktionierenden CI/CD-Prozess: Jeder Push löst automatisch einen Docker-Build aus und erzeugt ein lauffähiges Image. Die technische Grundstruktur ist damit beweisbar und reproduzierbar.

| Synchronisationsstrategie erfordert bewusste Entscheidung
| Der Spike hat gezeigt: LWW ist zu riskant (stille Überschreibung), CRDTs zu komplex für den Projektzeitraum (Komplexität 10/10). OCC (Optimistic Concurrency Control) ist der realistischste Kandidat. Diese Entscheidung muss noch als ADR formal dokumentiert werden und bleibt das wichtigste verbleibende technische Risiko des Projekts.

| Domänensprache stabilisiert den Projektrahmen
| Durch die kollaborative Arbeit am Miro-Glossar (24 Kandidatenbegriffe) und die anschließende Befüllung des Domain Glossary entstand eine einheitliche Projektsprache. Begriffe wie _Kündigungsfrist_, _Abrechnungszyklus_ und _Gastmodus_ sind eindeutig definiert und direkt in API-Modelle und User Stories übertragbar.

| Einheitliches Designkonzept
| Die wichtigsten Screens und deren Elemente wurden ausgearbeitet, um die in Sprint 1 erarbeitet Funktionen umzusetzen. Das Konzept wurde in Figma ausgearbeitet.

== 5. Architekturtreiber, Entscheidungen und technische Evidenz
[cols="1,3", options="header"]
|===
| Kriterium | Ihre Antwort

| Wichtigste Architekturtreiber
a|
* *DSGVO-Konformität*: Datensparsamkeit, kein PII in Logs, Recht auf Löschung → bestimmt Datenbankdesign und Authentifizierungsansatz
* *Gastmodus / Offline-Nutzung*: Nutzer sollen ohne Account und ohne Netzwerk Abos verwalten können → begründet lokale Datenhaltung als eigenständige Schicht
* *Benutzbarkeit*: Kernfunktion in unter 2 Minuten ohne Einarbeitung nutzbar → schlankes API-Design, kein unnötiger Overhead in der Datenstruktur
* *Projektlaufzeit* (1 Semester): kein Over-Engineering; Fokus auf tragfähiges Walking Skeleton + klar abgrenzbaren MVP-Ausschnitt für Sprint 3

| Wichtigste Entscheidungen / ADRs
a|
* *Django + REST API* als Backend-Kern: Teamkenntnisse, ORM-Unterstützung, schnelle API-Entwicklung; REST-Architektur ermöglicht spätere Frontend-Flexibilität (Web, Mobile)
* *Docker + GitHub Actions CI/CD*: reproduzierbare Builds ab Tag v0.0.1; Push-Trigger-Pipeline läuft stabil; verhindert Umgebungsunterschiede zwischen Teammitgliedern
* *OCC als Sync-Kandidat*: noch kein formales ADR — wird am Anfang von Sprint 3 entschieden, um Frontend-Anbindung zu ermöglichen

| Technische Evidenz
a|
* Tags v0.0.1–v0.0.5 im GitHub Repository: nachvollziehbarer Aufbau des Walking Skeleton mit korrekter Docker-Konfiguration
* Funktionierende CI/CD-Pipeline: Docker-Images werden automatisch gebaut und in Docker Hub gepusht
* Django REST API `/abos`-Endpoint: Abo-Daten können erfasst, gespeichert und abgefragt werden
* Datenbankmigrationen laufen ohne Fehler; saubere Projektstruktur ohne überflüssige Initialisierungsskripte

| Verbleibende Risiken / offene Fragen
a|
* ADR zur Synchronisationsstrategie (OCC vs. LWW) steht noch aus
* Authentifizierung / Nutzerverwaltung noch nicht im Walking Skeleton integriert
* Frontend-Anbindung an Backend noch nicht realisiert
* Kein automatisiertes Testkonzept; keine Test-Coverage vorhanden
* Kein Deployment-Konzept für Produktivumgebung definiert

|===


== 6. Anpassung der Arbeitsweise für Sprint 3

|===

| Beibehalten
a|
