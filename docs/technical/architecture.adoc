=== ADR-001: Backend mit Django

[cols="1,3"]
|===
| *Status* | Vorgeschlagen
| *Datum* | // TODO
| *Kontext*
| Es wird ein Backend mit Nutzerkonten, persistenter Datenhaltung und REST-API für die PWA benötigt. Account-basierte Synchronisation (siehe ADR-004) setzt ein robustes Auth-System voraus.
| *Entscheidung*
| Wir verwenden Django mit Django REST Framework, weil Auth, ORM und Admin out-of-the-box mitgeliefert werden und so Eigenentwicklung im begrenzten Semesterrahmen reduziert wird.
| *Alternativen*
| FastAPI/Flask (schlanker, aber Auth/ORM selbst zu bauen); Node/NestJS (zusätzlicher Tech-Stack neben Vue). // TODO: Team-Kenntnisstand als Begründung ergänzen.
| *Konsequenzen*
| Einfacher: Auth, Migrationen, Admin. Schwieriger/teurer: Django ist für klassische Request/Response ausgelegt — Echtzeit-Sync (WebSocket/SSE) erfordert Zusatzaufwand (Channels). Neues Risiko: keines wesentlich.
|===

=== ADR-002: Frontend als Progressive Web App (Vue) statt nativer Apps

[cols="1,3"]
|===
| *Status* | Vorgeschlagen
| *Datum* | // TODO
| *Kontext*
| Das Produktkonzept fordert Geräteunabhängigkeit (Android, iOS, Web). Das Review stufte native Geräteunabhängigkeit als aufwendig / „nice to have" ein. Die Projektlaufzeit beträgt ein Semester.
| *Entscheidung*
| Wir entwickeln eine PWA mit Vue.js, weil eine Codebasis alle drei Plattformen abdeckt und über Service Worker Installierbarkeit und Offline-Fähigkeit bietet — ohne den Aufwand zweier nativer Apps.
| *Alternativen*
| Native Apps (iOS+Android): zu hoher Aufwand für ein Semester. Reines responsives Web ohne PWA: keine Push-Benachrichtigungen, keine Installierbarkeit.
| *Konsequenzen*
| Einfacher: eine Codebasis, schnelle Iteration. Schwieriger: PWA-Fähigkeiten auf iOS Safari eingeschränkt (Service Worker, Web Push erst ab iOS 16.4 und nur bei „Zum Home-Bildschirm"). Neues Risiko: iOS-Zuverlässigkeit — wird über Spike validiert (siehe Risiken).
|===

=== ADR-004: Account-basierte Nutzung (Pflicht-Login)

[cols="1,3"]
|===
| *Status* | Vorgeschlagen
| *Datum* | // TODO
| *Kontext*
| Geräteübergreifende Synchronisation und zuverlässige serverseitige Erinnerungen erfordern eine Nutzeridentität. ACHTUNG: Im Sprint-Review wurde „Nutzung ohne Account" ausdrücklich positiv aufgenommen — diese Entscheidung steht im Spannungsverhältnis dazu, insbesondere zur Persona „Thomas der Skeptische" (Datenhoheit/Datensparsamkeit).

=== ADR-005: Deployment via Docker Compose auf HTW-VM (inkl. Scheduling)

[cols="1,3"]
|===
| *Status* | Vorgeschlagen
| *Datum* | // TODO

=== ADR-006: Benachrichtigung über Web Push

[cols="1,3"]
|===
| *Status* | Vorgeschlagen (Spike abgeschlossen; Android-Verifikation offen)
| *Datum* | // TODO
| *Kontext*
| Erinnerungen müssen Nutzende auch bei geschlossener App zuverlässig erreichen (Qualitätsziel: Hinweis ≥ 2 Tage vor Frist). Der Spike „Notification-Delivery" verglich Web Push und E-Mail (SMTP). Belegte Ergebnisse: Web Push funktioniert auf iOS (PWA, ab iOS 16.4, nach „Zum Home-Bildschirm"); E-Mail wäre über Port 587 (Submission/Relay) technisch möglich, Port 25 (direkte Zustellung) ist auf der HTW-VM blockiert. Web Push setzt technisch auf FCM (Google) bzw. APNS (Apple) auf — Datenschutz-/Datenhoheits-Implikation gegenüber Persona „Thomas der Skeptische".
| *Entscheidung*
| Wir verwenden *Web Push* als Benachrichtigungskanal. Begründung: kein E-Mail-Relay und keine HTW-IT-Freischaltung nötig (vermeidet die offene Relay-/Constraint-Frage), unmittelbare Zustellung, im Spike auf iOS bereits erfolgreich validiert. Der E-Mail-/SMTP-Weg wird *zurückgestellt* (nicht verworfen) und kann später als Zusatzkanal ergänzt werden.
| *Alternativen*
| E-Mail via HTW-Relay: datenschutzfreundlicher (kein Big-Tech-Dienst), aber Relay-Account, Projekt-Domain und SPF/DKIM/DMARC nötig sowie Klärung mit Anke — zurückgestellt. E-Mail via externer Dienst (Gmail/Brevo/SendGrid): kollidiert mit Constraint „keine kommerzielle Cloud" und Datenschutz-Positionierung — nur als dokumentierte Ausnahme. Reiner In-App-Reminder: erfüllt das Qualitätsziel NICHT (erreicht Nutzende nicht bei geschlossener App) — als alleiniger Kanal verworfen.
| *Konsequenzen*
| Einfacher: keine Mailserver-Infrastruktur, kein Relay-Vertrag, constraint-frei. Schwieriger / Risiken: (1) Abhängigkeit von FCM/APNS — Datenschutz-Trade-off, der der Privacy-Positionierung widerspricht und dokumentiert/kommuniziert werden muss; (2) iOS nur als installierte PWA und ab iOS 16.4; (3) *Android-Funktion noch nicht verifiziert* — offener Punkt. Push-Subscription-Endpoint je Gerät muss serverseitig gespeichert werden (Domänenmodell beachten).
|===
