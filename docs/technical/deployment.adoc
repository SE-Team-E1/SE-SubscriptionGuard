== Umgebungsübersicht

Das System wird in mehreren Umgebungen betrieben, die unterschiedliche Zwecke haben.
Lokale und CI-Umgebungen verwenden eigene Datenbanken und Testdaten und greifen
nicht auf die Datenbank der Demo-VM zu.

| Umgebung | URL | Zweck | Branch | Deployment

| Lokale Entwicklung

| Beliebig

| Lokale Integration

| Beliebig

Universitäts-VM sind SSH-Zugang und Docker bereits vorhanden.

== Lokale Entwicklungsumgebung

Diese Anleitung richtet sich an neue Teammitglieder, die das System zum ersten
Mal lokal zum Laufen bringen wollen.

=== Voraussetzungen

[cols="1,1,2", options="header"]
|===
| Werkzeug | Version | Installationshinweis

| Docker
| Bei Umsetzung festzulegen
| https://docs.docker.com/get-docker/

| Docker Compose
| V2; Mindestversion bei Umsetzung festzulegen
| Wird mit Docker Desktop mitgeliefert

| Git
| Aktuell
| https://git-scm.com

Die Entwicklungsserver laufen in Containern. Separate lokale Node.js- und
Python-Installationen sind für diesen geplanten Ablauf nicht erforderlich.

=== System lokal starten

Docker Compose startet Frontend, Backend und PostgreSQL vom Repository-Root aus. Das Setup funktioniert sowohl auf `main` als auch auf
Feature- und Feature-Integrationsbranches.

==== Entwicklungsmodus

* Vite und Djangos Entwicklungsserver laufen in Containern.
* Lokale Quellcodeverzeichnisse werden eingebunden, damit Änderungen beim
  Entwickeln ohne vollständigen Image-Neubau verfügbar sind.
* PostgreSQL läuft als eigener Service.

==== Integrationsmodus

* Frontend und Backend werden aus dem aktuellen Checkout in Images gebaut.
* Das Vue-Frontend wird als statischer Build von Nginx ausgeliefert.
* Django läuft mit Gunicorn.
* PostgreSQL ist Teil des lokalen Stacks.

Dieser Modus prüft die verpackte Anwendung und das Zusammenspiel der Services.
Die Verwendung der für das Deployment vorgesehenen Dockerfiles bedeutet kein
Deployment und keinen Zugriff auf Daten der Demo-VM.

==== Konfiguration und Testdaten

* Beide Modi verwenden eine gemeinsame Konfigurationsbasis mit modusspezifischen
  Anpassungen. Beispielkonfigurationen werden versioniert, Secrets nicht.
* Datenbankbereitschaft und Migrationen werden beim Start berücksichtigt.
* Lokale Daten bleiben über Neustarts erhalten.
* Ein wiederholbar ausführbarer Seed-Befehl erzeugt lokale Testkonten und
  Beispieldaten. Ein expliziter Reset-Befehl stellt einen sauberen Testzustand her.
* Start, Stopp, Moduswechsel und Datenreset werden dokumentiert.

==== Befehle

Für Start und Moduswechsel gibt es Shell-Skripte:

[source,bash]
----
./scripts/dev.sh          # Entwicklungsmodus starten
./scripts/integration.sh  # Integrationsmodus starten
./scripts/stop.sh         # Beide Modi stoppen, Daten behalten
----

Die Startskripte stoppen zuerst den bisherigen Modus, bauen die Images und
warten auf die Bereitschaft der Services. Datenbankdaten bleiben erhalten.
Die Skripte können auch über ihren vollständigen Pfad aus anderen Verzeichnissen
aufgerufen werden. Testdaten werden weiterhin explizit mit `seed_local` angelegt. Für die automatische
Anmeldung im Entwicklungsmodus wird standardmäßig das Konto `demo` verwendet.
Die entsprechenden direkten Compose-Befehle stehen im Folgenden.

Alle Befehle werden im Repository-Root ausgeführt. Root-`compose.yml` ist das
lokale Integrationssetup; `compose.dev.yml` ergänzt die Entwicklungseinstellungen.
Das ältere Compose-Setup unter `src/backend/django` ist davon unabhängig und wird
für diesen Ablauf nicht benötigt.

[source,bash]
----
# Optional: lokale Standardwerte überschreiben (bestehende .env behalten)
cp .env.example .env

# Integration: Images aus dem aktuellen Branch bauen und starten
docker compose up -d --build --wait

# Wiederholbar Testkonten und Beispieldaten anlegen
docker compose exec backend python manage.py seed_local

# Status und Logs
docker compose ps
docker compose logs -f backend frontend
----

Browser: http://localhost:8080; API-Dokumentation:
http://localhost:8080/api/schema/swagger/.
Die Datenbank und das Backend sind nicht direkt auf dem Host veröffentlicht.
Der Browser erreicht `/api` über Nginx beziehungsweise den Vite-Proxy.
`APP_PORT` in der optionalen Root-`.env` ändert den Browser-Port.

[source,bash]
----
# Erst den bisherigen Modus stoppen
docker compose down

# Entwicklung: Vite und Django-Entwicklungsserver mit lokalen Quellen
docker compose -f compose.yml -f compose.dev.yml up -d --build --wait

# Seed auch im Entwicklungsmodus ausführbar
docker compose -f compose.yml -f compose.dev.yml exec backend python manage.py seed_local
----

Die Entwicklung nutzt denselben Datenbank-Volume wie die lokale Integration.
Beim Wechsel zuerst stoppen, dann den anderen Modus starten. Nach einem
Branchwechsel stets `--build` verwenden. In Entwicklung wird `npm ci` beim
Containerstart ausgeführt; nach Lockfile-Änderungen den Frontend-Container neu starten.
Bei Python-Abhängigkeitsänderungen das Backend neu bauen.

Die Konten `demo` und `other-demo` erhalten beim ersten Seed das Passwort
`local-demo-password`, jeweils mit einem Beispielabonnement. Erneutes Seeding
überschreibt weder bestehende Konten noch geänderte Beispieldaten.
Es sind normale Benutzerkonten ohne Administratorrechte.
`LOCAL_TEST_DATA=true` erlaubt das Seeding ausschließlich im lokalen Setup;
diese Einstellung gehört nicht ins VM-Deployment.

Beide lokalen Modi starten erst nach Datenbankbereitschaft und erfolgreichem
Migrationslauf. Die bekannten lokalen Zugangsdaten sind nur für die Entwicklung;
die Dienste sind am Host ausschließlich über die Loopback-Adresse erreichbar.

=== System stoppen und aufräumen

[source,bash]
----
# Stoppen: lokale Daten bleiben erhalten
docker compose down

# Entwicklungsmodus stoppen
docker compose -f compose.yml -f compose.dev.yml down

# Bewusster Reset: löscht die lokale PostgreSQL-Datenbank vollständig
docker compose down -v
docker compose up -d --build --wait
docker compose exec backend python manage.py seed_local
----

`down -v` löscht im Entwicklungsmodus zusätzlich das Node-Abhängigkeitsvolume,
wenn beide Compose-Dateien angegeben werden. Es betrifft nur das lokale
Compose-Projekt `subscriptionguard-local`.

=== Häufige Probleme beim lokalen Start

[cols="2,3", options="header"]
|===
| Problem | Lösung

| Port bereits belegt (`address already in use`)
| Belegenden Prozess prüfen oder vorherigen Stack stoppen. Standardport: 8080; bei Konflikten `APP_PORT` ändern.

| Datenbank-Container startet nicht
| Compose-Status und Datenbanklogs prüfen. Ein Datenreset erfolgt nur bewusst,
  da dabei lokale Daten verloren gehen.

| Umgebungsvariablen fehlen
| Lokale Konfiguration mit der zugehörigen Beispielkonfiguration abgleichen.

| Weitere Probleme
| Mit der Umsetzung und den ersten Tests ergänzen.
|===

== Docker & Container

Dieser Abschnitt beschreibt, wie das System containerisiert ist, welche Container
existieren, wie sie konfiguriert werden, und wie sie zusammenarbeiten.

=== Container-Übersicht

[cols="1,1,2,1", options="header"]
|===
| Service | Image | Zweck | Port (intern → extern)

| Frontend
| Lokaler Build bzw. versioniertes Release-Image
| Vue-Anwendung; Vite in Entwicklung, statischer Build mit Nginx bei Integration und Deployment
| 8080 → `127.0.0.1:8080` (über `APP_PORT` anpassbar)

| Backend
| Lokaler Build bzw. versioniertes Release-Image
| Django-API; Entwicklungsserver in Entwicklung, Gunicorn bei Integration und Deployment
| 8000 intern, kein Host-Port

| Datenbank
| `postgres:16-alpine`
| Persistente Anwendungsdaten; getrennte Daten pro Umgebung
| 5432 intern, kein Host-Port
|===

Frontend und API sollen unter einer gemeinsamen Adresse erreichbar sein;
`/api` wird zum Backend geroutet. Die HTTPS-Einbindung auf der VM ist noch offen.

=== Umgebungsvariablen

Die Konfiguration soll über Umgebungsvariablen erfolgen. Versionierte
Beispielkonfigurationen dokumentieren die benötigten Werte ohne echte Secrets.

[cols="1,1,2,1", options="header"]
|===
| Variable | Beispielwert | Beschreibung | Pflicht

| `APP_PORT`
| `8080`
| Lokaler Browser-Port; in der Root-`.env` überschreibbar
| Nein

| `SECRET_KEY`
| Nur lokaler Standardwert in `.env.example`
| Django-Schlüssel; für VM später eigenen geheimen Wert verwenden
| Lokal vorbelegt

| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`
| Lokale Standardwerte in `.env.example`
| PostgreSQL-Zugang; gleicher Wert für Datenbank und Backend
| Lokal vorbelegt

| `USE_POSTGRESQL`, `DB_HOST`, `DB_PORT`
| `true`, `db`, `5432`
| Im lokalen Compose festgelegte Datenbankverbindung
| Ja

| `DEBUG`
| `false` für Integration, `true` für Entwicklung
| Django-Debugmodus
| Durch Compose gesetzt

| `LOCAL_TEST_DATA`
| `true` ausschließlich lokal
| Erlaubt den expliziten Seed-Befehl
| Für Seeding

| `API_PROXY_TARGET`
| `http://backend:8000`
| Serverseitiges Proxy-Ziel von Vite im Entwicklungscontainer
| Durch Entwicklungs-Compose gesetzt

| `LOCAL_API_USERNAME`, `LOCAL_API_PASSWORD`
| `demo`, `local-demo-password`
| Lokale Entwicklungsanmeldung; Compose übergibt diese Werte als
  `VITE_DEV_API_USERNAME` und `VITE_DEV_API_PASSWORD` an Vite.
  Die Werte sind im Browser sichtbar, daher nur Testkonten verwenden.
| Lokal vorbelegt
|===

IMPORTANT: Passwörter, Schlüssel und Tokens werden nie in Git gespeichert.
Lokale und VM-spezifische Secrets bleiben außerhalb des Repository-Verlaufs;
Registry-Zugangsdaten für die Pipeline werden als CI-Secrets verwaltet.

== CI/CD-Pipeline

Die Pipeline automatisiert Qualitätsprüfung und Veröffentlichung der Release-Images.
Das Deployment auf die nur über VPN erreichbare VM bleibt manuell.
CI schützt das durch Tests abgedeckte Verhalten vor Regressionen;
erfolgreiche Prüfungen ersetzen keine vollständige fachliche Abnahme.

=== Branches und Integration

`main` ist der gemeinsame Integrationsbranch. Änderungen gelangen über Pull
Requests mit erfolgreichen erforderlichen CI-Prüfungen nach `main`.
Ein Merge löst kein Deployment und keine Veröffentlichung von Release-Images aus.

* Unabhängige, rückwärtskompatible Änderungen können direkt per PR nach `main`
  gelangen. Dazu gehören neue Backend-Endpunkte, die bestehendes Verhalten
  erhalten und später vom Frontend verwendet werden können.
* Änderungen, die voneinander abhängen und nicht sicher einzeln integriert
  werden können, werden zuerst auf einem Feature-Integrationsbranch gemeinsam
  integriert und getestet. Anschließend erfolgt ein gemeinsamer PR nach `main`.
* Kleinere Teilbranches können in den Feature-Integrationsbranch zusammengeführt
  werden. Ein dauerhafter `staging`-Branch ist nicht erforderlich.

CI schützt das durch automatisierte Tests abgedeckte bestehende Verhalten vor
Regressionen. Zusätzlich prüfen Integrationstests vollständige Abläufe über die
Komponentengrenzen hinweg. Abhängige Änderungen werden vor dem Merge auch mit
dem lokalen Integrationssetup getestet; das Ergebnis wird im PR festgehalten.

=== Pipeline-Schritte im Detail

PRs nach `main` prüfen den vorgeschlagenen Merge-Stand. PRs auf
Feature-Integrationsbranches werden ebenfalls geprüft. Fehlgeschlagene
erforderliche Checks blockieren den Merge.

[cols="1,2,1,1", options="header"]
|===
| Schritt | Beschreibung | Schlägt fehl bei | Ausgeführt bei

| Linting
| Frontend mit vorhandenem ESLint und Oxlint prüfen, ohne Dateien automatisch zu ändern
| Lint-Fehlern
| PRs, Merges nach `main`, Release-Tags

| TypeScript und Frontend-Build
| Typkorrektheit und Paketierbarkeit prüfen; `npm run build` umfasst bereits beides
| Typ- oder Build-Fehlern
| PRs, Merges nach `main`, Release-Tags

| Unit- und Backend-Tests
| Frontend-Unit-Tests sowie Django-Tests gegen PostgreSQL
| Fehlschlagenden Tests
| PRs, Merges nach `main`, Release-Tags

| Migrationsprüfung
| Modelländerungen ohne zugehörige Django-Migration erkennen
| Fehlenden Migrationen
| PRs, Merges nach `main`, Release-Tags

| Integrationstests
| Vollständigen Compose-Stack starten und reale Abläufe prüfen
| Fehlschlagenden Tests oder Stack-Start
| PRs, Merges nach `main`, Release-Tags

| Image-Build
| Frontend- und Backend-Images bauen; bei PRs und Merges nicht als Release veröffentlichen
| Build-Fehlern
| PRs, Merges nach `main`, Release-Tags

| Image-Veröffentlichung
| Versionierte Frontend- und Backend-Images nach erfolgreichen Checks in GHCR veröffentlichen
| Fehlern bei Veröffentlichung
| Release-Tags
|===

==== Tests gegen den vollständigen Stack

Die bestehende Cypress-Infrastruktur soll für Tests gegen das echte Backend
erweitert werden. Gemockte API-Antworten allein prüfen dieses Zusammenspiel nicht.
Jeder CI-Lauf erhält eine saubere Testdatenbank mit definierten Testdaten.

Die erste Abdeckung umfasst:

* Registrierung beziehungsweise Anmeldung.
* Anlegen eines Abonnements über das Frontend.
* Erneutes Laden und Prüfen der gespeicherten Daten.
* Prüfung, dass Nutzer nicht auf fremde Abonnements zugreifen können.

Feature-PRs ergänzen oder aktualisieren die relevanten automatisierten Tests.
Bei Fehlern sollen Logs und Cypress-Screenshots zur Diagnose verfügbar sein.
Der temporäre Stack wird nach dem Testlauf entfernt.

=== Pipeline-Konfiguration

Die Workflow-Dateien liegen unter `.github/workflows/`.
Vorhanden ist `docker-image.yml`; dessen Anpassung und die Aufteilung der
geplanten CI- und Release-Workflows erfolgen bei der Umsetzung.
Eine automatisierte Deployment-Pipeline zur VM ist zunächst nicht vorgesehen.

== Deployment-Ablauf

=== Staging und lokale Integration

Die Integration erfolgt über `main` beziehungsweise Feature-Integrationsbranches
und das lokale Docker-Setup. Ein Merge nach `main` startet CI, aber kein
Deployment auf eine gehostete Staging-Umgebung.

=== Release und Deployment auf Produktion (manuell)

Mit Produktion ist hier die Hochschuldemo auf der Universitäts-VM gemeint.

Jedes Teammitglied darf einen getesteten Commit auf `main` als Release auswählen.
Der Versions-Tag muss genau den geprüften Commit referenzieren, auch wenn `main`
inzwischen weitere Änderungen enthält.

. Einen getesteten Commit auf `main` auswählen und einen Versions-Tag erstellen.
. CI prüft den getaggten Commit erneut und baut sowie veröffentlicht versionierte
  Frontend- und Backend-Images in GHCR. Veröffentlichung erfolgt erst nach
  erfolgreichen Prüfungen.
. Ein Teammitglied verbindet sich mit dem Universitäts-VPN und per SSH mit der VM.
. Ein wiederholbar ausführbares Deployment-Skript wird mit der gewählten Version
  gestartet. Es lädt die zugehörigen Images, führt Migrationen aus und startet
  beziehungsweise aktualisiert die Services mit Docker Compose.
. Smoke Checks prüfen, ob Frontend und API nach dem Deployment erreichbar sind.

Ein kurzer Wartungszeitraum ist für die Hochschuldemo akzeptabel.
Auf der VM verbleiben die Deployment-Konfiguration, lokale Secrets und persistente
PostgreSQL-Daten. Frontend und API sollen unter einer gemeinsamen Adresse
mit Routing von `/api` zum Backend erreichbar sein.

==== Offene Infrastrukturdetails

* Hostname und HTTPS-Zertifikat: Universitätszertifikat oder selbstsigniertes
  Zertifikat; Bereitstellung und Erneuerung sind noch offen.
* Ausgehender Zugriff der VM auf GHCR und gegebenenfalls notwendige
  Registry-Zugangsdaten müssen vor dem ersten Deployment geprüft werden.
* Konkrete Versionskonvention, Image-Referenzen, Deployment-Befehle und
  Health-Check-Endpunkte werden bei der Umsetzung festgelegt.

=== Smoke Tests nach Deployment

Nach jedem Deployment sollen die folgenden Prüfungen ausgeführt werden.
Die genauen Endpunkte und Befehle werden bei der Umsetzung ergänzt.

[cols="2,2", options="header"]
|===
| Prüfung | Erwartetes Ergebnis

| Frontend-Startseite laden
| Frontend wird erfolgreich ausgeliefert.

| API-Erreichbarkeit
| Backend antwortet über das vorgesehene Routing.

| Login-Flow
| Erfolgreiche Anmeldung mit einem Demo-Testkonto möglich.

| Kernfunktion prüfen
| Konkreten Umfang bei Umsetzung festlegen.
|===

== Rollback

NOTE: Backup und Recovery sind nachrangig und kein Blocker für die erste
Deployment-Umsetzung. Die folgenden Punkte beschreiben den späteren Zielzustand.

=== Wann wird ein Rollback durchgeführt?

* Kritische Fehler in der Demo nach einem Deployment.
* Smoke Tests schlagen nach Deployment fehl.
* Die vorherige Version muss für eine Vorführung wiederhergestellt werden.

=== Rollback-Ablauf

. Vor dem Deployment PostgreSQL sichern und bisherige Image-Versionen festhalten.
. Bei Fehlern die vorherigen Images wiederherstellen, sofern das Datenbankschema kompatibel bleibt.
. Falls Migrationen dies verhindern, zusätzlich die Datenbanksicherung wiederherstellen.
  Änderungen seit der Sicherung gehen dabei verloren.
. Smoke Tests ausführen und die Ursache untersuchen.

Konkrete Befehle, Automatisierung und Wiederherstellungsprüfung werden erst in
der späteren Ausbaustufe ergänzt. Dieser Ablauf ist noch keine verfügbare Funktion.

== Umsetzungsreihenfolge

. Lokale Docker-Modi für Entwicklung und Integration einschließlich Konfiguration,
  Testdaten und dokumentierten Befehlen bereitstellen.
. PR-CI einschließlich Tests gegen den echten Stack und erforderlichen Merge-Prüfungen einrichten.
. Versionierte Release-Images bei Tags bauen und veröffentlichen.
. Wiederholbares manuelles Deployment auf der Universitäts-VM bereitstellen.
. Backup- und Recovery-Werkzeuge ergänzen und Wiederherstellung testen.
